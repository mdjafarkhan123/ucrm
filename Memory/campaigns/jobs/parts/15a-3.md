# Part 15a-3: the Schedule asks a field worker for their own visits

Approved by Jafar 2026-09-07 after Jobber settled the product question. Code is written, committed as
`06b8685`, and **not yet applied or verified**. What is left is one coherent stage: apply, measure, check live.

## Settled, do not reopen

Jobber's Help Center (User Permissions) is explicit: Field crew "can see their own schedule" and "cannot see
another person's schedule"; the whole-company calendar is a separate, higher rung (Crew lead). So an
assigned-scope member's Schedule is their own, with no way to widen it until a permission that does not yet
exist is built. `Design/schedule-visits-research/official/jobber-dispatch-interactions.md` § Schedule
permissions carries the citations, and records that Jobber does **not** document the filter/lane presentation
for such a user -- that half was our design call, made as: drop every control whose only possible result is
empty.

## What is built

- `permission_scopes` on `EffectiveOrganizationAccess` + `permissionScope()` in
  `src/lib/server/access/permission.ts`. Mirrors `private.member_permission_scope`; both access resolvers now
  share one `resolveMemberPermissions` rather than a third copy of the block.
- `/api/schedule/visits` drives the visit and assessment reads from the caller's assignments when scope is
  `'assigned'`, via a second aliased `!inner` embed named `mine`. Proven live against the remote database:
  filtering `mine` leaves the sibling `assignments` embed complete, so a card keeps its whole crew.
- `20260910110000_field_assigned_scope_assessment_visibility.sql` -- `private.can_view_assessment`, and the
  assessment select/update/delete policies. Assessments were missed by 15a-2 and still let any member see
  every assessment in the business.
- The page reads `scope` back: no Employee filter, no Unassigned pile, no coworkers' lanes, Map opens on the
  viewer, tab title "My Schedule".

## Do not redo

- `private.can_view_job` and `private.can_view_assessment` are deliberately flat single statements that
  duplicate `has_permission` / `permission_scope`. RLS runs them once per scanned row and nested SECURITY
  DEFINER calls do not inline; nesting them again is the 938 ms 15a-2 measured.
- The select strings in the route are whole literals on purpose. supabase-js parses a select at the type
  level and an interpolated or union select collapses every field to an error type.

## Known, deliberately not fixed here

- `/api/schedule/unscheduled` still asks org-wide. It is bounded by `visit_date is null` and the same 200-row
  cap, so it is not on the growth path this part addresses -- but it has not been measured.
- Assessment **insert** still allows any member. Who may book an assessment is a Requests question, not a
  Schedule one.
