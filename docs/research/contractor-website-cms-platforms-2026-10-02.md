# Git-backed contractor website CMS: primary-source findings (2 October 2026)

## Hosting and publishing

- Cloudflare Pages can connect a project to a GitHub repository and build automatically when the production branch receives a commit. It also builds preview branches and pull requests, with a separate preview URL. A failed build does not become a successful production deployment; Pages offers rollback to a prior successful production deployment. [Git integration](https://developers.cloudflare.com/pages/configuration/git-integration/), [Astro guide](https://developers.cloudflare.com/pages/framework-guides/deploy-an-astro-site/), [rollbacks](https://developers.cloudflare.com/pages/configuration/rollbacks/).
- Current **Free** Pages limits are 500 builds/month, one concurrent build per account, 20-minute build timeout, 100 Pages projects/account, 20,000 files/site, and 25 MiB/site asset. These are account/project limits, so a separate Pages project per contractor will outgrow one Free account at 100 sites and may queue publishes well before that. This is a planning constraint, not a claim about actual customer capacity. [Pages limits](https://developers.cloudflare.com/pages/platform/limits/).
- For a client's root domain (`example.com`), the domain must be a Cloudflare zone **in the same account as the Pages project** and its registrar nameservers must point to Cloudflare. A subdomain can instead use a CNAME at another DNS provider. The client can remain the registered domain owner while granting operational DNS access; nameserver delegation is distinct from transferring registration. [Pages custom domains](https://developers.cloudflare.com/pages/configuration/custom-domains/), [Cloudflare full DNS setup](https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/).
- Cloudflare Pages does not create preview URLs for PRs from forked repositories. It also currently cannot move a Git-integrated Pages project to Direct Upload or change its linked repository without creating a new project. Those details affect CMS choice and ownership transfer. [GitHub integration](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/), [known issues](https://developers.cloudflare.com/pages/platform/known-issues/).

## Managed-site client access pattern

Wix Studio lets an agency give a client a **content-only mode**: the client changes text and images but cannot change the design. Webflow similarly separates content editing from structural and code changes, and its publishing right can be granted separately. This supports a useful middle ground for Uplift: a genuine Website area and, if sold, a narrow content editor; there is no need to expose a full page builder merely to give a contractor control. [Wix Studio client access](https://support.wix.com/en/article/wix-studio-inviting-a-client-to-join-a-site), [Webflow content editor](https://help.webflow.com/hc/en-us/articles/33961251014931-Edit-site-content-as-a-content-editor).

Wix also distinguishes the site owner from collaborators, and the owner can transfer ownership. That distinction matters for Uplift's sales wording: contractor ownership of the domain and supplied content should be stated separately from access to the managed source and hosting. [Wix roles and ownership](https://support.wix.com/en/article/roles-permissions-overview).

## Existing editors against the stated ownership rule

| Option | Documented model | Fit with CRM-only access and no contractor Git access |
| --- | --- | --- |
| Decap CMS GitHub backend | Edits GitHub repo files; every normal editor needs GitHub push access. Editorial workflow saves drafts to branches/PRs and merges on publish. [GitHub backend](https://decapcms.org/docs/github-backend/), [editorial workflow](https://decapcms.org/docs/editorial-workflows/) | Direct use conflicts with no Git access. Its Open Authoring allows external GitHub users without write access, but uses forks and requires a maintainer to merge; fork PR previews are unsupported by Pages. [Open Authoring](https://decapcms.org/docs/open-authoring/), [Pages GitHub integration](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/) |
| Decap Turbo | Hosted authentication/proxy lets editors work without Git host accounts; saves still become Git commits. [How it works](https://decapcms.org/docs/turbo-how-it-works/) | Closer, but adds a separate vendor account/seat and requires verifying CRM subscription integration and site-scoped roles before choosing it. |
| Keystatic GitHub mode | Astro integration exists; GitHub-mode collaborators need repository write access. Its deployed Astro editor needs server-side code/Node APIs and an adapter. [Astro install](https://keystatic.com/docs/installation-astro), [GitHub mode](https://keystatic.com/docs/github-mode) | Direct mode conflicts with no Git access and is more deployment-coupled than a static Astro site with a separate editor. |
| Keystatic Cloud | Lets editors without GitHub accounts edit a Git-connected project; team-level access covers all projects in the team, and Free currently allows 3 users/team. [Cloud docs](https://keystatic.com/docs/cloud) | Possible, but tenant isolation would require separate teams or other controls, and login would still be a vendor identity unless an integration is established. |
| TinaCMS | Official Astro integration and visual editing exist. Visual refresh uses on-demand Astro routes/SSR adapter, even when site pages are static. Self-hosted backend on Astro requires manual setup. [Astro setup](https://tina.io/docs/frameworks/astro), [visual editing](https://tina.io/docs/contextual-editing/astro), [self-hosting](https://tina.io/docs/self-hosted/existing-site) | More editing power, but adds runtime and backend complexity to otherwise static sites; validate Cloudflare compatibility and the desired auth model in a prototype. |

## Architecture implication (inference from the cited product behavior)

The closest match to "contractor signs into CRM, edits only their own website, never receives Git/source access" is a **CRM-authorized editor and server-side publishing service**. The CRM checks active subscription and website membership; the server maps the website to an allowed private repository, validates edits against a page/content schema, stores drafts, and on publish writes only approved content paths to GitHub using a server-held GitHub App installation token. GitHub documents repository-scoped, short-lived installation tokens and `Contents` write permission for tree/commit operations. [GitHub App tokens](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app), [Git trees](https://docs.github.com/en/rest/git/trees).

This is a recommendation to evaluate, not evidence that a custom CMS should be built from scratch. Decap/Keystatic/Tina schemas and editing controls can be evaluated for reuse behind the CRM boundary. A first prototype should prove: one private Astro repo, one contractor-safe editor, image uploads, draft/preview, one publish commit, Pages deployment status, and rollback. Set an explicit policy for domain ownership, website source buyout, cancellation export, and retained content before launch; platform docs do not decide those contract terms.
