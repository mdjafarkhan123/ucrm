# Part 15a-4: permission rules stop running once per scanned row

Approved by Jafar 2026-09-07 ("fix it from the root"). Migration
`20260910120000_permission_checks_run_once_per_query.sql` is applied and committed as `c6b2474`. The database
half is done and verified. **What is left is the browser check and the behaviour contract.**

## What was wrong, so it is not reintroduced

Every job-family read policy was `is_organization_member(organization_id) AND can_view_job(organization_id,
job_id)`. Both take the row's own columns, so Postgres cannot hoist either: it re-ran the whole membership +
permission + scope lookup once per scanned row. That single fact, not the shape of any query, was the entire
cost of the Schedule -- the same read is 2.7 ms with RLS off.

It also explains why 15a-3's route narrowing failed and was reverted: no question the route can ask changes
how many times the rule runs.

## The shape now in place

- `private.current_organization()` and `private.current_permission_scope(key)` take no row-dependent
  argument, so a policy calls them as `(select ...)` and Postgres evaluates them once per statement as an
  InitPlan. Confirmed in the plans: `InitPlan 1/2` execute once, `InitPlan 3` is `never executed` for an
  'all'-scope member, and the organization test becomes a `One-Time Filter`.
- `private.is_assigned_to_job` / `is_assigned_to_assessment` are the only per-row half. One probe on the
  existing `job_visit_assignments_member_job_idx`; no new index. They stay SECURITY DEFINER because an
  inlined subquery over `job_visit_assignments` would recurse through that table's own policy.
- `can_view_job` / `can_view_assessment` are kept for their single-entity callers (`can_view_visit`,
  `can_view_job_expense`, `can_view_linked_entity`) but are re-expressed on the same primitives, so the scope
  rule exists once instead of three times.

Two schema facts it rests on, verified not assumed: `organization_members` has `UNIQUE (user_id)`, and every
job-family table reaches `jobs` through a composite `(organization_id, job_id)` foreign key.

## Known, deliberately not fixed here

  the jobs list plan shows it as a Seq Scan on `clients` and `properties`. Small at 11 and 8 rows, but it is
  the same defect and the same fix applies. Not touched here to keep the change to one family.

  `completed_at is null` and the route does not filter that, so the index cannot be used. 7 ms at 5,007 rows,
  but it grows with the tenant's lifetime assessments.
- `/api/schedule/unscheduled` still asks org-wide; bounded by `visit_date is null` and a 200-row cap, never
  measured.
- Assessment **insert** still allows any member. Who may book an assessment is a Requests question.
