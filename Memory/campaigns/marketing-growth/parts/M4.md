# M4 — Safe send, schedule, gradual delivery, cancellation

Approved 2026-09-22 by Jafar: build per-contractor verified SES sending identities now (not a shared
platform domain), five stages in order. Stages 1-2 approved to build. Pointing stage 1 at a real
contractor's live domain still needs a separate direct go-ahead.

## Why M4 became five stages

Research found the AWS SES/SNS/SQS pipeline is provisioned in the AWS console only — no application code
talks to SES at all. Reusable and proven: the operational outbox claim/finalize pattern, warmup ceiling,
reputation/suppression/pause tables (provider-agnostic, keyed by org+domain), the
`marketing_update_campaign_draft` P0409 optimistic-lock shape, and
`private.marketing_evaluated_recipients_sql` for eligibility.

## Stage 1 decisions (already made — do not re-litigate)

- Marketing sends from **`news.<root>`**, MAIL FROM **`bounce.news.<root>`** (under the marketing subdomain,
  so one suffix guard covers every written record). Separate from operational `mail.<root>`.
- New purpose value **`marketing_sending`**, so every existing `purpose='sending'` query keeps excluding it.
- Marketing `lifecycle_state='verified'` additionally requires `spf_status='passing'`.
- SES tenant + configuration set are **per organization** in `communication_ses_tenants`; identity per domain.
- Easy DKIM's three CNAMEs are the only proof of domain control SES issues, so `ownership_status` mirrors
  `dkim_status` rather than tracking a second, always-identical value.
- SES `TEMPORARY_FAILURE` maps to `pending`, not `failing` (SES retries it for up to 72 hours).
- Tenant/config-set names are derived (`ucrm-org-<orgId>`, `ucrm-marketing-<orgId>`), never stored-then-guessed.

## Open decision for stage 3 (not stage 1's to make)

What exactly the Marketing **From address** is. `src/lib/server/marketing/delivery-options.ts` still shows the
contractor's operational sender (`hello@mail.<root>`) in the campaign Review step, but a campaign will actually
leave from `news.<root>`. The established pattern (Mailchimp, Klaviyo, Brevo) is a From name + a From address on
the verified bulk domain, with Reply-To pointing at an address the contractor really reads. Recommendation:
derive `<operational sender local part>@news.<root>` with the same display name, Reply-To = the operational
sender. Decide this before the dispatcher sends anything, and update `delivery-options.ts` in the same change.

## Stage 2 state and decisions (already made — do not re-litigate)

- Tables are named **`marketing_email_allowance_periods`**, **`marketing_email_capacity_reservations`**, and
  **`marketing_campaign_recipients`** — by product area, the way `website_chat_allowance_periods` is, not the
  `communication_marketing_*` shorthand this packet first used.
- **One reservation per campaign, not the operational four-table shape.** Marketing reserves its whole eligible
  count once at launch, so `reserved_count` (held) and `accepted_count` (what SES took) on the reservation row
  are exact. No capacity-bucket table: with one allowance class, locking the period row is the serialization
  point, and it also keeps marketing launches off the operational send path's lock.
- Marketing gets **its own allowance period table** reading the same shared
  `private.current_communication_allowance_window`. `private.ensure_marketing_allowance_period` opens and locks
  it on demand; `marketing_launch_campaign` is its only caller, so the shared ensure/sweep functions were not
  touched.
- **Hard ceiling of 50,000 matched rows per launch**, refused above it. Measured locally: a 20,000-recipient
  launch is one transaction of ~900 ms; the paged recipient read is a pure index scan (53 buffer hits, 0.06 ms).
- The `marketing.launch` permission and the readiness checks stay in the calling route, as with every other
  marketing command; the RPC is service-role only.
- **Finding:** `client_contact_methods_org_value_unique_idx` already forbids two Customers in one organization
  sharing an email address, so the preview's `duplicate_destination` reason cannot arise from separate
  Customers. The launch keeps the same dedupe window as the preview so the two always agree, but the reason is
  effectively unreachable today.
- Stage 2 deliberately ships **no HTTP route and no UI**. A Send button that queues recipients no dispatcher
  reads would be worse than none; go-live is stage 5.
