## Why it is blocked: the narrowing does not narrow

Measured on a rebuilt 15a-2-shaped fixture (5,000 jobs, 45,000 visits over a year, field worker on 500 jobs →
868 visits in the week, 84 the worker's). Warm `EXPLAIN (ANALYZE, BUFFERS)`, remote database.

| Schedule, one week | Result |
| --- | --- |
| No RLS at all (floor) | **2.7 ms** |
| Owner, today | **161 ms** (scans 624 rows) |
| Field worker, org-wide read + RLS discard (the shape 15a-3 replaced) | **118 / 119 ms** |
| Field worker, `mine` inner join (**the shape 15a-3 ships**) | **216 / 238 ms** |
| Field worker, driven from the assignment index | **1,266 ms** |

`private.can_view_job` is the entire cost — ~0.14–0.25 ms per scanned row, ~15 buffers per row. The `mine`
embed does not change the driving side: the plan still walks `job_visits_calendar_idx` for the org's whole
week and still reports `Rows Removed by Filter: 787`. It only adds a join, so it roughly doubles the read.
Both halves of the target fail — it is not back toward 27 ms and it does not scale with the worker's
assignments. 15a-2's own narrowing also regressed the **owner's** Schedule from 27 ms to 161 ms; that was
never measured at the time.

Driving from `job_visit_assignments` is the worst option, not the fix: that table's RLS runs `can_view_job`
on all 4,501 of the worker's rows before the date window is applied.

So the bottleneck is the per-row SECURITY DEFINER call, not the question the route asks. No route-level
rewrite can fix it.

## Do not redo

- `can_view_job` / `can_view_assessment` are deliberately flat single statements that duplicate
  `has_permission` / `permission_scope`. Nesting them again is the 938 ms 15a-2 measured. Flattening them
  further is not the remaining win — the remaining win is calling them fewer times.
- The select strings in the route are whole literals on purpose. supabase-js parses a select at the type level
  and an interpolated or union select collapses every field to an error type.
