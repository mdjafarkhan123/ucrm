# Proposed Invoice contract corrections

**Approved by Jafar and applied to `docs/invoice-behavior-contract.md` in the current session.**
Both issued retention through Void and reversal/replacement corrections are approved traceability improvements.
Research evidence: [matrix](invoice-jobber-evidence.md), [financial findings](invoice-payment-research.md).
The table below is the approved change record; its former proposal labels describe what was submitted.
This approval does not authorize schema design, implementation, or invented transition rules.

| Contract location | Current wording / omission                                                                | Proposed correction                                                                                                                                                                                                                                                                                                                                           |
| ----------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity          | “Client owns a separate billing address”                                                  | “Client has one effective billing address, matching a designated Property or using a custom Client billing address. Included service locations remain distinct.” Existing snapshot safeguards are UCRM policy, not a claim about Jobber storage.                                                                                                              |
| Status            | Seven “displayed statuses,” including Sent Not Due                                        | Display Draft, Awaiting Payment, Past Due, Paid, Bad Debt, Voided. Treat Sent but not due as an overview grouping; future-due issued invoices display Awaiting Payment. Partial payment remains a separate fact.                                                                                                                                              |
| Creation/payment  | Draft collection is implicit                                                              | Explicitly allow collecting a manual payment on a Draft and Save-and-Collect. Full settlement makes Paid. Hold partial-draft transition rules open until verified.                                                                                                                                                                                            |
| Closure/balance   | Paid includes marked received, without explaining residual debt                           | Explain that Close without recording payment changes status but does not settle Client debt. Payment, write-off, and status-only closure have distinct consequences.                                                                                                                                                                                          |
| Bad Debt          | Reversible write-off only                                                                 | Add Client-balance removal of the unpaid remainder and Client-Hub hiding; retain invoice and reversibility. Do not send a cancellation message as an inferred Jobber behavior.                                                                                                                                                                                |
| Void              | Three reasons and broad “unpaid eligible”                                                 | Include Other; reasons internal. Exclude progress invoices as documented. Preserve irreversible retention, deposit release, and notification intent. Leave partially paid eligibility unresolved. UCRM email first; SMS remains deferred.                                                                                                                     |
| Issued deletion   | No explicit issued-deletion policy                                                        | **Proposed departure:** after issue, retain through Void instead of Delete; drafts remain deletable after confirmation. Jobber permits issued Delete. Retention preserves the original bill and its correction trail. Progress invoices need a verified alternative because Jobber excludes them from Void; do not invent one.                                |
| Manual methods    | Broad wallet/financing categories                                                         | Only Other, Bank transfer, Cash, Check, Credit/debit card (external), PayPal. All acknowledge money received elsewhere.                                                                                                                                                                                                                                       |
| Corrections       | Reversing/adjusting entries presented as baseline; includes failed-payment infrastructure | **Proposed departure:** corrections retain the original financial record and use an explicit reversal/replacement to explain the change. Jobber permits manual edits/deletion. This preserves traceability without pretending it is Jobber's storage model. Remove failed-ACH/processor/dispute/payout/saved-card/auto-pay infrastructure from this campaign. |
| Payment terms     | One organization fallback; fixed option list                                              | Invoice override → Client term → residential/commercial default. Company-name identity uses commercial; unspecified type uses residential. Include documented term management and optional explicit promotion of Invoice terms to Client default; do not create an unverified client-type selector.                                                           |
| Batch             | Exactly one draft per Client                                                              | Group compatible work per Client; different property tax rates split invoices. Explicitly disclose that Jobber can invoice selected incomplete Visits and marks them complete. Confirm this cross-contract consequence before implementation.                                                                                                                 |
| Delivery/parity   | Broad Jobber capability baseline                                                          | Name initial email/manual-payment scope as a subset. Standard-mail batch PDFs/labels and provider behavior are documented Jobber features, not automatically authorized additions.                                                                                                                                                                            |
