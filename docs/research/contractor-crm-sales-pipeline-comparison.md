# Contractor CRM sales-pipeline comparison

Research date: 2026-08-18  
Scope: first-party product and help documentation for Jobber, Housecall Pro, ServiceTitan, JobNimbus, Buildertrend, FieldPulse, and HighLevel

## Conclusion

Leading contractor products do **not** converge on one freely editable opportunity stage running independently from operational records. Their dominant pattern is a pipeline view derived from, or tightly coupled to, the real contractor objects: lead/request, assessment, estimate/quote, job, and approval/sale. The products differ mainly in how much manual customization they permit around those system states.

For UCRM, the strongest fit is a **hybrid lifecycle pipeline**: one active commercial thread can be followed from Request through Quote, but its core columns are system-owned projections of Request/assessment/Quote state; optional custom follow-up stages can sit around those columns. Request and Quote remain distinct source records and retain their own screens. Won/Lost is an opportunity outcome, not a user-defined stage, and approved domain events should set it automatically. This matches contractor-native behavior better than a generic, fully manual HighLevel-style deal board.

## Pattern comparison

### 1. Separate domain boards

Housecall Pro is the clearest implementation: Lead, Estimate, and Job each have a board. This makes status ownership obvious and prevents a pipeline card from contradicting its source record. Its cost is a fragmented sales overview and a handoff between boards.

### 2. Unified lifecycle view over domain records

Jobber provides one visual board spanning Requests and Quotes, but the board does not replace their states. Core columns are system-owned and domain actions move cards; custom stages supplement those states. ServiceTitan is more rule-driven still, deriving pipeline membership and outcomes from Jobs and Estimates. This is the dominant pattern most aligned with UCRM's Request → Quote → Job lifecycle.

### 3. Freely customizable record workflow

JobNimbus allows deep workflow customization, but statuses still belong to contractor Job records and map into fixed lifecycle stages. FieldPulse attaches customizable sales state to Customers. HighLevel is the pure general-CRM model: an independent Opportunity can move through arbitrary stages and automations. The more generic the model, the greater the risk of duplicate or contradictory truth in a contractor system.

## Recommendation for UCRM

1. **Keep Request and Quote as the source of truth.** Their approved status machines, permissions, history, and actions must not be duplicated in an editable Opportunity stage.
2. **Show one active commercial thread when records are related.** A Request that becomes a Quote should remain visually continuous, even though the underlying records are distinct. Avoid Jobber's surprising presentation of every Request and Quote as separate simultaneous opportunities unless UCRM intentionally supports multiple competing Quotes as separate deals.
3. **Use protected system stages for domain facts.** A sensible initial spine is New Request → Assessment Unscheduled → Assessment Scheduled → Assessment Completed → Quote Draft → Awaiting Response → Changes Requested. The exact labels should reuse approved Request and Quote terminology.
4. **Allow custom follow-up stages only at explicit insertion points.** Examples are Qualification, Contacted, Site Visit Follow-up, and Quote Follow-up. Moving into them changes only sales workflow state. Moving into a protected system stage must run or request the corresponding domain action, as Jobber does.
5. **Model outcome separately from stage.** Use Open, Won, and Lost, with a structured lost reason. Quote approval should normally set Won automatically because Jobber and ServiceTitan both derive success from the accepted/sold Estimate or Quote. If UCRM intentionally requires manual `Mark Won`, record that as a deliberate divergence and guard against an approved Quote remaining Open indefinitely.
6. **Do not extend the sales pipeline through Job execution, Invoice, or Payment.** Those belong to operational and financial workflows. Housecall Pro separates them; JobNimbus's broader Job board is useful operationally but is not evidence that the sales opportunity should remain open.
7. **Support standalone opportunities only if they represent pre-Request qualification.** Buildertrend supports a true Lead Opportunity before a presale Job. If UCRM allows this, conversion should create/link the Request and preserve history rather than leaving two unrelated active records.

## Decision still needed

Choose between these two defensible presentations while keeping the same protected domain model:

- **Single lifecycle board:** Request and Quote system stages appear together, with one card continuing across conversion. Best for small contractor teams and closest to Jobber's at-a-glance experience.
- **Two board tabs:** Requests and Quotes have separate boards with a shared opportunity identity and combined reporting. Clearest status ownership and closest to Housecall Pro.

A fully free-form single Opportunity pipeline is not recommended as UCRM's default. It follows general CRM convention, but the contractor-native evidence favors domain-derived stages or separate domain boards.
