# Part 8B — Complete organization export

**Approved by Jafar 2026-09-25:** owner-only; background job + email notification (not instant download,
not in-app-only); includes metadata + link manifests + checksums + the actual blobs (a real backup), not
metadata alone.

## Design (grounded in this codebase's existing patterns, not invented)

- **Permission:** new key `files.export`, scope_model `none`, mapped to role `owner` ONLY in
  `role_permissions` (stricter than `files.manage`'s owner/admin/office spread — matches the roadmap's
  explicit "owner-only").
- **Table `organization_exports`:** id, organization_id, requested_by, status
  (`queued`/`processing`/`available`/`failed`/`expired`), object_key, file_count, total_bytes, error,
  requested_at, completed_at, expires_at. RLS: SELECT only, gated on `files.export`. No insert/update
  policies — writes go through SECURITY DEFINER RPCs, service-role only, exactly like `create_file_share`
  (`20260925100000_files_media_customer_shares.sql`): the API route checks permission, then calls the RPC
  with the service-role client (`getOwnerSupabaseClient()`).
- **RPCs:** `request_organization_export` (dedupes against an already-queued/processing row for the org),
  `claim_next_organization_export` (`for update skip locked`, one row), `finalize_organization_export`,
  `purge_expired_organization_exports` (clears `object_key`, sets `expired` — never deletes the row, same
  "keep history, clear storage" call Jafar made for 8A's Trash purge).
- **No download token.** Unlike the 7D customer share, this is owner-only and the owner is already
  signed in — the email is a plain notification ("sign in and download"), not a bearer link. The download
  route re-checks `files.export` + org match and hands back a presigned R2 URL
  (`createPresignedDownloadUrl`, `src/lib/server/storage/r2.ts`). Simpler and more secure than minting a
  token for a feature that never needs an anonymous reader.
- **Two worker cadences, reusing the existing shape (`processing-worker.ts`, one route per job family):**
  - Heavy build gets its OWN route `/api/internal/files/export-worker` and its OWN cron
    (`files-export-worker-wake-five-minutes`, every 5 min) with a long `timeout_milliseconds` (30 min) —
    NOT bolted onto the existing one-minute route, whose cron entry is hard-capped at 60s and would abort a
    multi-minute zip build. Reuses the same `FILES_PROCESSING_WORKER_SECRET` bearer value (no new secret to
    manage) but needs its own Vault URL secret `files_export_worker_target_url` pointing at the new route —
    new deployment gate item, added to ROADMAP.md's approval gates.
  - Cheap purge sweep (`purge_expired_organization_exports`) joins the existing per-minute route's sweep
    section, same as 8A's trash purge — indexed, usually 0 rows.
- **Zip build:** stream each `available` File's object out of R2 straight into a zip entry and the zip's
  bytes straight into an R2 multipart upload — never buffer the whole export in memory (same philosophy as
  `processing-worker.ts`'s one-read-per-file comment). New deps: `archiver` (streaming zip) +
  `@aws-sdk/lib-storage` (`Upload`, handles the multipart upload from a stream). A purged File
  (`object_key is null`) is listed in the manifest but has no blob in the zip, with a note why — mirrors
  the customer-facing "Photo removed" permanence from 8A.
- **Manifest:** `manifest.json` at the zip root — one entry per File (id, name, mime type, size, checksum,
  created/trashed/purged timestamps) plus its `file_links` rows (entity_type, entity_id, role, protected).
  Built in TS from plain selects (service-role client), not a SQL function — this is a read/report, not a
  business rule, so it doesn't need to live in Postgres like the write-path RPCs do.
- **Scope of "permitted blobs":** owner sees the whole org, so this is every File in the org whose
  `processing_state = 'available'` — including currently-trashed-but-not-yet-purged ones (a full backup
  should not omit something the owner could still restore).
- **Known, accepted limitation:** no chunked/resumable zip build across multiple cron ticks — a single
  invocation builds the whole thing. Fine at today's realistic org sizes; genuinely large orgs (the kind
  Part 7B-3 load-tested for *listing*) have not been load-tested for *export build time*. Say so plainly if
  asked about capacity — no capacity claim without evidence, matching the campaign-wide rule.

## Not yet decided / verify while building
- Exact `expires_at` window for a completed export's download — defaulting to 7 days (matches Google
  Takeout's default, and is shorter than the 30-day Trash/share windows since a multi-GB zip sitting in R2
  costs real storage). Flag to Jafar if it should differ.
- Frontend surface: an "Export everything" action in the Files workspace toolbar (`files.export`-gated),
  not a new Settings page — this is a Files-and-Media capability, not a general settings toggle.
