Approved 2026-09-22 by Jafar: build per-contractor verified SES sending identities now (not a shared
platform domain), five stages in order. Stages 1-2 approved to build. Pointing stage 1 at a real

## Why M4 became five stages

Research found the AWS SES/SNS/SQS pipeline is provisioned in the AWS console only — no application code
talks to SES at all. Reusable and proven: the operational outbox claim/finalize pattern, warmup ceiling,
reputation/suppression/pause tables (provider-agnostic, keyed by org+domain), the
`marketing_update_campaign_draft` P0409 optimistic-lock shape, and
`private.marketing_evaluated_recipients_sql` for eligibility.

## Stage 1 decisions (already made — do not re-litigate)

- Marketing sends from **`news.<root>`**, MAIL FROM **`bounce.news.<root>`** (under the marketing subdomain,
  so one suffix guard covers every written record). Separate from operational `mail.<root>`.
- New purpose value **`marketing_sending`**, so every existing `purpose='sending'` query keeps excluding it.
- Marketing `lifecycle_state='verified'` additionally requires `spf_status='passing'`.
- SES tenant + configuration set are **per organization** in `communication_ses_tenants`; identity per domain.
- Easy DKIM's three CNAMEs are the only proof of domain control SES issues, so `ownership_status` mirrors
  `dkim_status` rather than tracking a second, always-identical value.

- Tenant/config-set names are derived (`ucrm-org-<orgId>`, `ucrm-marketing-<orgId>`), never stored-then-guessed.

## Stage 2 state and decisions (already made — do not re-litigate)

- Tables are named **`marketing_email_allowance_periods`**, **`marketing_email_capacity_reservations`**, and
  **`marketing_campaign_recipients`** — by product area, the way `website_chat_allowance_periods` is, not the
  `communication_marketing_*` shorthand this packet first used.
- **One reservation per campaign, not the operational four-table shape.** Marketing reserves its whole eligible
  count once at launch, so `reserved_count` (held) and `accepted_count` (what SES took) on the reservation row
  are exact. No capacity-bucket table: with one allowance class, locking the period row is the serialization
  point, and it also keeps marketing launches off the operational send path's lock.
- Marketing gets **its own allowance period table** reading the same shared
  `private.current_communication_allowance_window`. `private.ensure_marketing_allowance_period` opens and locks
  it on demand; `marketing_launch_campaign` is its only caller, so the shared ensure/sweep functions were not
  touched.
- **Hard ceiling of 50,000 matched rows per launch**, refused above it. Measured locally: a 20,000-recipient
  launch is one transaction of ~900 ms; the paged recipient read is a pure index scan (53 buffer hits, 0.06 ms).
- The `marketing.launch` permission and the readiness checks stay in the calling route, as with every other
  marketing command; the RPC is service-role only.
- **Finding:** `client_contact_methods_org_value_unique_idx` already forbids two Customers in one organization
  sharing an email address, so the preview's `duplicate_destination` reason cannot arise from separate
  Customers. The launch keeps the same dedupe window as the preview so the two always agree, but the reason is
  effectively unreachable today.
- Stage 2 deliberately ships **no HTTP route and no UI**. A Send button that queues recipients no dispatcher
  reads would be worse than none; go-live is stage 5.

## Stage 3 decisions (already made — do not re-litigate)

Approved by Jafar 2026-09-22: the From-address pattern (`<operational sender local part>@news.<root>`, same
display name, Reply-To = the operational sender) and building stage 3 now, ahead of the AWS credentials.

- The claim/finalize pair lives on `marketing_campaign_recipients` directly (no shared outbox-event table like
  operational email): `claim_marketing_campaign_recipient()`, `finalize_marketing_campaign_send(...)`,
  `quarantine_stale_marketing_campaign_claims(...)`. Migration:
  `supabase/migrations/20260922170000_marketing_campaign_dispatcher.sql`. pgTAP:
  `supabase/tests/database/marketing_campaign_dispatcher.sql` (26 assertions, all passing locally).
- No per-row `available_at`/backoff column: a recipient that cannot send right now (org pause, domain not
  verified, warmup ceiling) is simply left `waiting` for the next one-minute wake. Bulk marketing is not
  time-sensitive the way a receipt/reminder is, so this is deliberately simpler than the operational outbox.
- A quarantined stale claim becomes `submission_unknown` (new enum value), never `waiting` — SES may have
  already accepted the send, so a blind retry risks a duplicate. A `retry` outcome gives up after 3 attempts
  (`failed`), since there's no backoff clock to space attempts out.
- Per-recipient eligibility is rechecked at claim time via `private.marketing_recipient_blocked_reason(...)`,
  which mirrors `private.marketing_evaluated_recipients_sql`'s per-row logic exactly (same priority order:
  inactive_customer, missing_email, complaint, unsubscribed/hard_bounce, do_not_disturb, no_marketing,
  no_consent) — a customer who unsubscribes mid-campaign is excluded, not sent.
- Warmup ceiling reuses `private.resolve_communication_email_warmup_ceiling` (generic, table-driven) but counts
  *marketing's own* submitted rows today, not the operational usage tables — those never reference the
  marketing domain at all.
- Completion + reservation settlement is folded into `finalize_marketing_campaign_send`: when a campaign's
  last `waiting`/`checking` recipient resolves, the campaign flips to `completed` and its single reservation
  settles with `accepted_count` = however many actually reached `submitted`.
- Cron: `dispatch_communication_marketing_worker_wake()` + `communications-marketing-outbox-wake-one-minute`
  job, same shape as the email/SMS dispatch functions, reading the shared `communications_worker_secret`
  Vault secret and a new `communications_marketing_worker_target_url` one. Installed but inert (like SMS
  before its launch gate) until that URL secret and the `AWS_SES_*` values both exist.

## Stage 4 decisions (already made — do not re-litigate)

Approved by Jafar 2026-09-22: build stage 4 now, ahead of AWS credentials, same as stage 3.

- **Own event log table, not a shared one.** `communication_provider_callback_events` is structurally locked to
  Brevo/Twilio (`provider_channel_check`) and keyed to `communication_delivery_intents`, which marketing has
  none of. Mirrors stage 2's own-table precedent: new table `marketing_campaign_recipient_events` (same shape
  as the operational callback log: raw payload, `provider_event_key` unique for idempotency, `processed_at`/
  `processing_attempts` for the batch drain). RLS enabled, no policies — service-role only, same as the
  operational table.
- **No SNS envelope to unwrap.** The provisioned SNS topic delivers to SQS with raw message delivery, so an
  SQS message body is the bare SES event JSON.
- **Correlate by `provider_message_id`**, already stored on `marketing_campaign_recipients` by stage 3's
  finalize. No new send-time tagging needed.
- **Idempotency key:** `ses:<mail.messageId>:<eventType>`. A duplicate insert (23505) is treated as
  already-recorded, same as the Brevo webhook, and the SQS message is deleted either way once durably
  recorded or confirmed duplicate.
- **No app-level quarantine.** SQS's own visibility timeout is the retry mechanism; an unprocessed message
  becomes receivable again on its own. A message that fails to parse is left undeleted so AWS's own
  maxReceiveCount(5) DLQ policy on `ucrm-ses-events-dlq` catches it, not a bespoke poison-pill table.
- **Two sticky terminal statuses, mirroring `process_communication_provider_callbacks`'s
  hard_bounce/complaint guard:** `bounced` and `complained` can overwrite `delivered`/`submitted` and each
  other, but nothing (including a later `Delivery` event) can overwrite `bounced`, `complained`, or
  `unsubscribed` (the last is set elsewhere, by the customer's own click — this consumer only guards it).
  `Bounce` events with `bounceType=Permanent` map to `bounced`; `Transient`/`Undetermined` map to a soft
  bounce that leaves `status` alone (SES retries internally, same as stage 1's `TEMPORARY_FAILURE` decision).
  `Reject` maps to `failed` (guarded the same way). `DeliveryDelay`/`Send`/anything unrecognized is logged
  only, no status change.
- **Reuses `communication_email_suppressions` as-is** for hard_bounce/complaint, exactly like the operational
  processor. `source_callback_event_id` stays null (its FK targets the operational table, a different table
  now) — `evidence` jsonb carries the same detail plus `campaign_id` for traceability.
- **Deliberately does NOT touch `communication_email_reputation_state` / `evaluate_communication_email_reputation`.**
  That evaluator currently measures only operational sends; wiring marketing bounces into it would change a
  proven safety mechanism and is a bigger, separate decision. Flagged below as unresolved, not stage 4's to
  decide.
- **Worker/cron naming**, same shape as stage 3: worker name `communications-marketing-events`, cron function
  `dispatch_communication_marketing_events_worker_wake()`, job `communications-marketing-events-wake-one-minute`,
  its own Vault secret `communications_marketing_events_worker_target_url` (shares
  `communications_worker_secret` for the bearer). Installed inert until Jafar sets that secret and the
  `AWS_SES_*` values exist.
- **Queue URL is derived, not stored**: `https://sqs.<region>.amazonaws.com/<accountId>/ucrm-ses-events`, from
  the same account id `ses-env.ts` already extracts out of `AWS_SES_EVENT_SNS_TOPIC_ARN` — no new env var.
- **New dependency:** `@aws-sdk/client-sqs` (first SQS consumer in the codebase; nothing existing to reuse for
  the receive/delete calls themselves).
- **Projector RPC `project_marketing_campaign_recipient_events(batch_size)`** mirrors
  `process_communication_provider_callbacks`'s shape (`FOR UPDATE SKIP LOCKED`, bounded batch, try/catch per
  row with a processing-attempts giveup), service-role only.
