## 15a-2, fully designed and ready to build

1. `public.job_visit_assignments` carries only `visit_id` (`20260901025502_*.sql:78`). Add `job_id`, made
   impossible to drift by a composite FK, plus index `(organization_id, user_id, job_id)`. This is the
   performance gate's verdict: without it the "am I on this job" test walks every visit of the job, and a
   two-year weekly recurring job has ~100.
2. `jobs.view` sets `scope_model = 'assigned_or_all'` in `public.permissions` — the first permission ever to
   do so. Until one does, a trigger (`private.assert_scope_is_supported`, `20260822055549_*.sql`) refuses to
   store `access_scope = 'assigned'`. Then set Field's `role_permissions.access_scope` to `'assigned'`.
3. Extend **`private.can_view_job`** (created in 15a-1 for exactly this) with
   `permission_scope(org,'jobs.view') <> 'assigned' or exists(assignment for this caller and job)`. Every
   note, tag, attachment and activity row inherits it for free.
4. Sweep the shipped `jobs.view` gates. Two kinds:
   - **11 table SELECT policies** — jobs, job_events, job lines, job visits, job visit assignments,
     recurrence rules, invoice reminders, payment stages, visit lines, time entries, expenses. The list
     views (`job_list_rows`, status counts, invoice reminders) are `security_invoker = true`, so fixing the
     `jobs.jobs` policy fixes them for free — confirmed, do not rewrite the views.
   - **~14 SECURITY DEFINER read models** that check `member_has_permission(..., 'jobs.view')` themselves and
     so bypass RLS. Only the *latest* definition of each name is live: `job_money` (20260901102141),
     `job_line_money` (20260901002848), `schedule_calendar_context` (20260902101500), `job_schedule_money` /
     `visit_line_money` (20260906113542), `job_schedule_stages` (20260906190000), `job_visit_lines`
     (20260908130000), `can_view_job_expense` (20260908170000), `can_write_job_time` / `job_labor`
     (20260908180000), `can_write_job_expense` / `job_expenses_list` (20260908190000), `job_costing`
     (20260908200000 and 20260908210000). Each needs a `member_job_is_visible(org, caller, job_id)` variant.
5. Narrowing view opens a write hole: a Field member holds `jobs.complete` and the completion commands check
   only that key, so they could complete a visit on a job they can no longer see. Add the visibility
   precondition to `complete_job_visit` / its uncomplete twin.
6. Fill in `private.client_is_assigned_to_current_user` (`20260816110139_*.sql:105`, still `select false;`).
   `20260824135801_*.sql` says it was always meant to key off Visit assignment "until Scheduling exists".
7. Verification owed by the performance gate: EXPLAIN ANALYZE of the job list and the Schedule date-window
   read, as a field worker with ~500 assignments in a 5,000-job tenant, before and after.

## Non-obvious risks, already paid for once

- Widening a polymorphic seam is **four** edits, not three: 15a-1's RLS test failed because
  `private.log_note_link_activity` writes into `activity_events`, whose entity_type check nobody had widened.
  Always attach a real record in the test rather than reasoning about it.
- Test RLS by impersonating a real member inside a `do $$ ... $$` block that ends in
  `raise exception 'ROLLBACK_WITH_RESULTS >> %'` — it reports the results and rolls everything back.
- `src/lib/database.types.ts` is 400KB and cannot be regenerated in-conversation; any new table owes it.
  15a-1 owed nothing — entity_type is plain `text`, and the new helpers live in `private`.
